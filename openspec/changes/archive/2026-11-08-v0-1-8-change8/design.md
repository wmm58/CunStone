# Design

## Context

当前实现虽然完全在浏览器运行，但应用外壳仍围绕本地账号设计：`App.tsx` 根据 `activeUser` 守卫路由，`authService` 维护 `users` 和 `activeUserId`，`WorkRecord` 带 `ownerId`，`workService` 按当前账号过滤作品，P1 登录页和三页的“切换账号”都依赖这套模型。localStorage 当前为 v7，并保留 v1–v7 的迁移链。

Change 8 的动机与行为见 `proposal.md` 和 `specs/`；本文只记录实现方式。

## Goals / Non-Goals

**Goals:**

- 删除账号、登录和所有权概念，使应用成为无需身份上下文的单用户本地工具。
- 把 localStorage 收敛为只包含作品集合的 v8 数据。
- 打开应用任何有效入口都直接落到创作编辑页。
- 生成适配 Gitee Pages 子路径的纯静态构建，不依赖服务端路由重写。
- 保持图片处理、黑白编辑、作品预览、A4 排版和 PDF 的现有行为。

**Non-Goals:**

- 不提供旧 v1–v7 数据迁移、恢复或备份。
- 不提供账号、权限、分享、统计数据、远程管理或云同步。
- 不改变 P2 的图片处理算法和 P3/P4 的核心渲染口径。
- 不引入 PWA、Service Worker 或离线安装。

## Decisions

### 决策 1：应用外壳不再有身份守卫

`AppRoute` 删除 `login` 分支，路由默认进入 `editor` 新建作品页：

- 根路径、空 Hash 和旧 `#/login` 都重定向到 `#/editor/new`。
- 无法识别的 Hash 也回退到 `#/editor/new`，避免空白页。
- `App.tsx` 删除 `getActiveUser`、`signOut` 和所有 `activeUser` 条件。
- `LoginPage` 与 `authService` 及其测试删除，不再保留隐藏账号模式。

选择直接删除账号，而不是保留“本地单用户 profile”，因为用户明确要求不需要账号，单用户身份也没有任何可见价值。

### 决策 2：localStorage 直接升级为 v8

当前根状态从：

```
{ version, activeUserId, users, works }
```

收敛为：

```
{ version: 8, works }
```

`WorkRecord` 删除 `ownerId`，`LocalUser` 类型删除。读取时只接受 v8：

- 无数据：返回空 v8 状态。
- v1–v7 或损坏数据：删除应用存储键，返回空 v8 状态，并标记一次性重置恢复类型。
- 当前 v8 非法数据：同样清空并回到空作品库。

不保留旧迁移代码和旧版本 fixture，也不保留历史 `drawing` 来源、`broken` 边框或粗线换算兼容。采用直接重置而不是迁移，是因为用户已明确允许删除当前浏览器旧作品。

### 决策 3：作品服务改为本地库 API

`workService` 去掉 `getActiveUser` 依赖和 `no-active-user` 错误，函数按当前浏览器作品库工作：

- `createWork`
- `updateWork`
- `getWork`
- `listWorks`
- `listWorksByStatus`
- `deleteWorks`

`getWork` 查找失败只表示本地作品不存在；`deleteWorks` 忽略不存在的 ID，并通过一次 `writeAppState` 完成批量删除。页面层不得再把 `not-found` 解释为“不属于当前账号”。

选择重命名函数而不是保留 `listActiveUserWorks` 等旧名字，因为这些名称会继续暗示不存在的账号模型。

### 决策 4：三个核心页面保持现有职责

- 创作编辑页：保留 P2 全部编辑、保存、清除和直接 A4 导出行为。
- 作品列表页：保留 P3 筛选、预览、继续编辑、多选、删除和 A4 导出。
- A4 导出页：保留 P4 添加作品、排版和 PDF 下载。

页面标题继续使用“创作编辑”“作品列表”“A4 导出”，删除 P1 登录页。源文件和测试内可继续保留 `P2/P3/P4` 的稳定标识，避免无意义的大规模重命名；用户界面不显示 P 编号。

### 决策 5：账号相关 UI 与文案全部移除

- P2、P3、P4 删除“切换账号”按钮和 `onSignOut` props。
- P3 删除“当前账号：手机号”提示。
- P2 保存弹窗只说明当前浏览器保存范围，不再出现“本地账号仅用于区分作品”或权限隔离文案。
- P2 未保存离开只覆盖“作品列表”等应用内导航，不再描述切换账号。
- 错误文案统一为“作品不存在”或“本地数据不可用”，不再提账号归属。

### 决策 6：静态资源使用相对基础路径

Vite 生产构建使用相对资源基础路径（`base: "./"`），使 `index.html` 能在 Gitee Pages 的任意项目子路径下加载同一目录中的 JS/CSS 资源。路由继续使用 Hash：

- 不依赖 History API 回退。
- 不要求 Gitee Pages 配置 SPA 重写。
- 刷新 `#/works`、`#/export/a4` 仍返回同一静态入口。

选择相对基础路径而不是把仓库名写死，是为了同时支持本地预览、仓库 Pages 子路径和未来自定义域名。

### 决策 7：旧数据重置显示一次性提示

应用启动读取到旧版本时执行重置，并在创作编辑页显示一次非阻断提示，例如“旧版本本地数据已清空，已使用空白作品库启动”。提示不阻止用户继续创建作品，也不再提供恢复入口。

### 决策 8：测试按新入口重写

现有 Change 1–7 集成测试大量使用固定登录作为前置步骤，实现时必须统一替换为直接进入编辑页：

- 路由测试覆盖根路径、旧登录路径和未知路径。
- 存储测试覆盖空 v8、合法 v8、旧 v7 清空和损坏数据清空。
- 作品服务测试覆盖无账号创建、列表、更新、删除和未知 ID。
- P2→P3→P4→PDF 集成测试不再包含登录/切换账号。
- 静态构建检查覆盖子路径资源和 Hash 路由刷新。

## Risks / Trade-offs

- **旧作品永久丢失** → 用户已明确接受；实现只在旧版本检测时清空并显示一次提示，不提供迁移或恢复。
- **同一浏览器使用者共享全部作品** → 这是单用户本地工具的预期行为；页面明确本地数据边界，不宣称权限隔离。
- **Gitee Pages 子路径资源失效** → 使用相对 `base` 构建，并在子路径静态服务器下做构建产物验收。
- **Hash 路由外链不美观** → 以静态托管兼容性优先；不引入服务端重写依赖。
- **localStorage 容量限制** → 保持现有单浏览器存储边界，不新增云端或大文件归档能力。
- **删除 `change1` 全部要求会退役该历史 capability** → 新 `local-work-library` 接替作品生命周期；归档时验证主 specs 不残留登录要求。

## Migration Plan

1. 将应用外壳与路由改为无登录直接入口，删除登录页和认证服务。
2. 将领域类型、localStorage 和作品服务改为 v8 单用户作品库。
3. 更新 P2/P3/P4 的 props、文案和导航，移除账号操作。
4. 更新测试与静态部署配置，生成 `dist` 并在子路径静态服务器验证。
5. 更新 README、工程基线、蓝图、线框图和包版本为 `0.1.8`。
6. 发布到 Gitee Pages；回滚旧版本前应清空 v8 本地数据，避免旧代码误读新结构。

## Open Questions

无。旧数据删除、无账号入口、Hash 路由和 Gitee Pages 静态托管口径已由用户确认。
