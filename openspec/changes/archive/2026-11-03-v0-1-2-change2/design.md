# 设计（Design）

## Context

Change 1 已实现 Vite + React + TypeScript + Tailwind CSS 前端、localStorage v1 数据层、P1 登录、P2 外壳、本地账号与作品元数据。当前 `WorkRecord` 只有名称、状态和时间字段，P2 中央区域仍是占位画布。

Change 2 需要在不引入服务端 API、外部 AI 或新后端的条件下，把 P2 扩展为本地图片输入与预处理页面。工程基线要求所有数据继续保存在当前浏览器的 localStorage 中。

## Goals / Non-Goals

**目标：**

- 在 P2 增加外形、实际尺寸、图片上传、手绘输入、纯色背景点选、容差、剪影/轮廓和自动适配。
- 使用浏览器 Canvas/ImageData 在本地生成纯黑白基础稿。
- 将输入图片和处理参数保存进作品，并在同一浏览器恢复。
- 把 localStorage 数据结构从 v1 平滑升级到 v2，保留 Change 1 数据。

**非目标：**

- 不创建自建 API、服务端、数据库或外部 AI 调用。
- 不实现 Change 3 的画笔、橡皮、撤销重做、线宽、阴阳刻、镜像和边框。
- 不处理复杂背景、多色背景、渐变背景或透视四角校正。
- 不实现 P3 作品列表、P4 A4 排版或 PDF 导出。
- 不在 P2 显示 Change 1 已排除的独立红印/黑白预览面板。

## Decisions

### 决策 1：所有图片处理在浏览器本地完成

使用原生 Canvas 2D、`ImageData` 和 TypeScript 纯函数完成解码、去底、裁切、缩放、锐化、轮廓提取和黑白化。不引入图片处理 API，也不增加服务端。

考虑过的替代方案：调用外部 AI 抠图 API。该方案违反当前工程基线和 Change 2 的本地处理边界，因此不采用。

### 决策 2：作品数据升级到 v2，并保留 v1 数据

`WorkRecord` 增加 `imageState`。`imageState` 保存：

- 输入来源：上传或手绘，未输入时为空。
- 源图片：压缩后的 Data URL。
- 印章外形：正方形、长方形、圆形或自定义。
- 实际宽度和高度（毫米）。
- 用户点选的背景颜色。
- 背景容差 0–100。
- 效果类型：剪影或轮廓。
- 处理算法版本。

localStorage 结构版本由 1 升级到 2。读取 v1 数据时必须迁移用户、作品、状态和活动账号，并为旧作品补上空输入状态与默认外形尺寸，不能清空 Change 1 数据。

### 决策 3：只持久化源图和参数，不持久化派生黑白图

黑白稿是由源图、颜色、容差、效果、外形和尺寸确定性计算出的派生结果。Change 2 只保存压缩源图和参数，重新打开时重新计算黑白稿。

这样避免同时保存原图和黑白图导致 localStorage 快速超限。Change 3 增加手动编辑后，再根据新的编辑状态设计保存方式。

### 决策 4：限制上传文件和工作分辨率

接受 PNG、JPEG、WebP，单文件上限 10 MB。图片解码后在最长边不超过 1600 像素的工作画布上处理；持久化源图优先使用浏览器支持的 WebP 压缩，无法编码时回退为 PNG。

考虑过的替代方案：保存用户原始高清图。该方案容易超过 localStorage 容量，因此 v0.1 不采用。

### 决策 5：手绘输入只是“输入工具”，不是 Change 3 编辑工具

手绘入口提供固定线宽黑色画笔和清空重画，支持鼠标与触控笔。Change 2 不提供橡皮、撤销重做、线宽选择或手绘图层；这些属于 Change 3 的黑白稿编辑范围。

### 决策 6：纯色去底使用像素颜色距离

用户在输入画布点击背景像素后，系统记录该 RGB 颜色。容差滑杆 0–100 映射为 RGB 欧氏距离阈值；距离小于等于阈值的像素变为透明，随后在黑白稿中显示为白色。

容差默认值为 20。容差变化时重新计算预览，但不自动识别背景颜色，也不处理多色或渐变背景。

### 决策 7：自动适配采用确定性几何处理

处理流程：

1. 根据图片元数据归一化方向。
2. 按容差生成保留主体掩码。
3. 计算主体可见内容的包围盒并裁掉透明外边距。
4. 按所选印章外形等比缩放并居中，保留约 5% 内边距。
5. 使用印章外形进行裁切，圆形使用圆形裁切。
6. 执行固定强度的本地锐化并二值化。

“矫形”在 Change 2 中定义为方向归一化、透明边裁切、居中缩放和外形裁切，不包含透视四角校正。

### 决策 8：剪影与轮廓使用同一主体掩码

- 剪影：对二值化后的主体掩码填黑，其余区域为白色。
- 轮廓：在主体掩码边界提取黑色边缘，其余区域为白色。

最终输出逐像素只允许 `#000000` 和 `#FFFFFF`，透明区域也必须渲染为白色。自动锐化只用于改善二值化前的边缘，不得产生灰色像素。

### 决策 9：P2 中央画布使用“输入 / 黑白稿”两种查看模式

输入模式用于上传、手绘、点击背景和容差预览；黑白稿模式展示处理后的基础稿。两种模式共用同一个中央画布区域，不新增独立结果页，也不引入 Change 1 已排除的预览面板。

左侧区域严格对应线框的 01–04：

- 01 外形与实际尺寸
- 02 输入完整画面
- 03 纯色背景去除
- 04 效果与适配

### 决策 10：自动保存源图和参数

已有作品的源图、外形、尺寸、背景颜色、容差和效果发生变化后，继续使用 Change 1 的自动保存机制。源图上传或手绘完成后立即保存；容差滑杆等高频变化做短暂延迟后保存，手动保存仍可立即落盘。

localStorage 写入失败时保留当前内存画布并显示错误，不静默丢失输入。

### 决策 11：像素处理逻辑与 Canvas 渲染分离

去底、容差、包围盒、缩放、轮廓和二值化逻辑实现为接收 `ImageData`/像素数组的纯函数；Canvas 层只负责解码、绘制和事件坐标换算。这样可以在 jsdom 中不依赖真实 Canvas 实现完成核心算法测试。

## Risks / Trade-offs

- localStorage 容量有限 → 限制源图分辨率、压缩源图、只保存源图和参数，并复用已有容量错误提示。
- 纯色容差会造成主体误删或边缘残留 → 容器提供实时预览，残留边缘由 Change 3 橡皮擦继续修整。
- 自动适配可能无法满足所有构图 → Change 3 继续提供手动黑白编辑；Change 2 不承诺透视校正。
- Canvas 2D 在大图上阻塞界面 → 最长边限制 1600 像素，并对高频滑杆变化做延迟处理。
- 浏览器 Canvas/编码能力存在差异 → 在支持的桌面浏览器中测试 WebP 编码回退与 Canvas 2D 可用性。
- v1 数据迁移错误会丢失 Change 1 数据 → 为 v1→v2 迁移编写专门测试，并保留原用户、作品和活动账号。

## Migration Plan

1. 将 `APP_STORAGE_VERSION` 从 1 升级到 2。
2. 为 v1 作品补充默认 `imageState`：无源图、正方形、25 mm、容差 20、剪影效果。
3. 读取 v1 时在内存中迁移，并在应用初始化/下一次保存时写回 v2。
4. 读取到损坏数据或高于 v2 的版本时沿用现有安全回退策略。
5. 若 v2 写入失败，保留迁移后的内存数据和当前画布，提示用户重试。

## Test Strategy

- 纯函数单元测试：颜色距离、容差、包围盒、缩放、剪影、轮廓和二值化。
- 数据测试：v1→v2 迁移、图片状态持久化、容量写入失败。
- 组件测试：形状/尺寸控件、上传错误、手绘输入、背景点选、效果切换。
- 集成测试：上传固定样本 → 去底 → 容差 → 剪影/轮廓 → 保存 → 同浏览器重新打开并恢复。
- Canvas 测试使用轻量 2D context mock，不依赖真实浏览器绘制结果。

## Open Questions

- 桌面浏览器最低版本尚未确认；实施时至少需要支持 Canvas 2D、`ImageData` 和所需的本地图片编码能力。
