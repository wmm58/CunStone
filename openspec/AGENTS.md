## Git 提交规范（唯一真源）

- 提交信息必须包含 `Co-authored-by: 你的名字 <你的邮箱>`；禁止添加 AI 工具签名/广告。
- 默认中文提交信息；标题可用约定式短前缀（如 `feat`/`fix`/`docs`/`chore(scope)`）。
- 功能类提交正文至少写清：做了什么 / 改了哪里 / 行为与兼容性影响 / 验证结论。
- 未做真项目验收时，验证结论必须写明「仅本地验证，未做真项目验收」。
- 纯文档提交可精简，但仍需说明校对方式。

提交示例（功能类）：

```text
feat: 完成 C6 扫码签到与状态流转

- 变更内容：两个入口扫码/查询签到，名单状态更新并追加进场记录
- 影响文件：src/features/checkin/、openspec/changes/v0-1-6-checkin-flow/
- 兼容性：仅新增签到链路，不改变既有报名与凭证行为
- 验证：npm run build 通过；npm run test:run 全部通过；openspec validate --strict 通过

Co-authored-by: 你的名字 <你的邮箱>
```

提交示例（文档类，可更短但仍写验证）：

```text
docs: 补充提交规范示例

- 补充功能类与文档类提交示例，明确标题、正文结构与验证结论写法
- 仅更新 AGENTS.md，不涉及运行时代码行为变更
- 验证：人工校对示例字段齐全（变更内容/影响文件/兼容性/验证/署名）

Co-authored-by: 你的名字 <你的邮箱>
```

## 版本号与发布策略（唯一真源）

- 语义化版本 `MAJOR.MINOR.PATCH`。0.x 阶段无对外消费者，**MINOR = 阶段蓝图切换**，**线内一切交付一律 PATCH** — 新子命令、新能力不因「对外新增」跳号拆大版本（杜绝 semver 教条）。
- **一个 change 对应一个精确版本号，成功交付后对应一个 tag**：change 后缀即该 change 的目标版本；禁止多个 change 共指同一个 tag。版本号不节俭 — 每个已交付 change 各占一格 PATCH；已对外提交的失败版本同样占号，不回收、不补同号修订。
- 正式发布用 annotated tag `vMAJOR.MINOR.PATCH`；禁止强推覆盖已发布 tag。
- **发布标准顺序**：更新版本号并完成门禁验证 → 提交 → 打 tag → 发布 → 校验一致性（tag ≡ `--version` ≡ 发布台账）。顺序不颠倒，不先打 tag 后补验证。
- **发布遇到问题立即升版**：一经对外提交审核或发布，发现需要修订的问题，立即新起下一个未占用的 PATCH 版本修复、验收并发布覆盖；不得继续在旧编号下改包、反复提审或覆盖发布，也不得用 `R1`、`R2` 等同号修订绕过版本递增。
- **一个版本只对应一套正式交付产物**：版本号是本地目录、部署交接和各分发渠道上架的共同对账依据；修复升版后，所有产物按新版本交接清单逐项更新核对，避免同号覆盖造成源件混乱。
- 发布一致性：git tag ≡ CLI `--version` ≡ 发布台账记录，三处必须一致。
- 每次验收通过并正式收官后必须在发布台账新增一行；禁止修改历史行。已对外提交但验收失败的版本另记失败关闭记录，不伪造成功发布行。
- 本地构建产物采用「1+3」保留策略：`dist/` 仅保留当前正式版本及其之前最近三个正式版本，按版本/tag 顺序判断；清理只作用于本地构建产物，不得删除 Git tag、台账、源码或线上历史产物。

## 蓝图与版本对应（唯一真源）

- **开新 MINOR 线前，必须先立该线蓝图**：`docs/plans/v0.x/…-blueprint.md`。蓝图先行，蓝图内定 change 拆分与验收标准，该线的 change 才立项。蓝图缺失时，禁止开该线新 change。
- **四对应**：蓝图（线）↔ change（后缀=目标版本）↔ 版本号（tag）↔ 发布台账行。每个 change 必须能指回所属蓝图线；每个 MINOR 线必须有一份蓝图。
- 蓝图是活文档：线内追加 change 时同步更新蓝图映射表；线收官时文首状态行同步（已交付/候补/进行中）。
- **欠账处理**：已发生欠账必须候补蓝图，文首如实标注「候补（补写日期）」并按实际走线记账，禁止回改历史、禁止假装一直有蓝图。
- 线内补充计划文档（如标定记录、专项实现方案）放同目录，不占蓝图名。

## 工作区与双窗口协议（唯一真源）

- 工厂工作区对本仓开发会话**永远只读**。审计/复核只允许：读文件、ffprobe/ffmpeg 抽帧到 /tmp、jq 摘非凭证字段。凡写项目文件或产生计费的命令，必须用户明确授权；「顺手修复」「帮忙补跑」同样禁止。
- 出片由独立的生成窗口（Agent + skill + svf）执行；开发窗口影响出片行为的**唯一通道 = 版本发布**（改本仓 → tag → 升级二进制），不得直接改生成窗口的项目文件 — 那等于篡改对方的世界模型（一次真实事故的根源）。
- 审计必须快照式：读一次形成结论，不假设文件不变，不与生成窗口竞态写。

## 受限环境判定与运维输出纪律（唯一真源）

- 宿主沙箱或受限环境内命令失败（`Operation not permitted`、找不到命令、超时等），不能仅凭一次失败断言环境不可用、组件缺失或外部服务离线；先分层复核（非沙箱路径、用户侧可达性、其他证据）再定性。
- 复核确认为真实限制后，产品修复方向是去依赖或降级（绝对路径优先、移除硬依赖），不是要求用户绕过或手工代做。
- 运维与诊断类命令的输出、转述只允许非敏感结论（`configured=true/false`、字段是否为空、版本号、计数）；禁止回显密钥、口令、token、激活码明文与手机号。

## 提交前验证门禁（唯一真源）

1. `cargo fmt --all` 与 `cargo test` 通过。
2. `./scripts/secret-scan.sh --staged` 通过（命中高危密钥模式必须先修复；豁免仅允许走最小规则的允许清单）。
3. 涉及 OpenSpec change 时，`openspec validate <change-id> --strict --no-interactive` 通过。

纯文档改动（仅 `*.md`、不涉运行时行为与配置）可豁免第 1 条，但必须人工校对并在提交信息注明「纯文档提交」。

纯文档改动若包含以下任一情况，仍必须回到完整门禁：宣称某项新能力、行为、兼容性或性能结论已成立；修改安装、部署、配置或运维步骤，且这些步骤依赖尚未验证的新行为；更新验收结论、对外能力承诺或发布口径，但无对应实测证据（曾有不实对外文案正是从此缝溜出）。

开发过程中优先运行受影响路径的定向测试，实现收敛后集中执行上述本地门禁。已通过的检查，仅在后续改动、失败或新风险影响其结论时重跑，不为每个小改动反复执行整套验证。

## 发布/归档门禁（唯一真源）

- **按改动影响面验收**：每个 change 在设计与任务中写明受影响模块、平台、验证方式及扩测条件。局部修复验证修复路径和相邻回归面，不得仅因发了新版本就要求所有平台重复全流程。
- 未受影响平台保留必要的包完整性、版本与文档一致性检查；触及跨平台公共逻辑时，按实际影响补充该平台回归；受影响路径必须取得本版验证证据，不得用历史通过记录冒充。
- 成功交付归档 change、打 tag、宣称版本可用之前，必须完成**真项目验收**：在真实工作区用本工具独立完成该 change 范围内的真实生产验证（整体版本 = 独立产出一条完整成品）。
- 未完成真项目验收前，禁止按成功交付归档、创建发布 tag、宣称版本可用。
- **失败关闭归档例外**：明确决定停止当前版本、由新 PATCH 接替时，可将 change 以「验收失败 / 被后继取代」关闭归档。归档前必须记录失败证据、最终分发状态、原任务逐项处置及后继承接关系；失败或未执行任务保持未勾，不得改记通过。该归档不代表产品验收，不创建正式 tag、不新增成功发布台账行。

## 代码注释与体量治理（唯一真源）

- 注释一律中文；每个 `.rs` 文件首部必须有 `//!` 模块职责注释；公共项 `///`；行内 `//` 只解释「为什么」。
- 源码文件 401-600 行：新增代码必须说明是否可拆；601-800 行：本次 change 必须包含拆分任务；超过 800 行：禁止继续堆叠，先拆分。
- `mod.rs` 收紧一档：目标 ≤400 行，上限 600 行，超过视为结构违规，先拆分再合入。
- 例外（生成代码等）必须在变更说明中写明原因与治理计划。

## 测试组织与稳定性（唯一真源）

- 组织形态沿用现状：单元测试就近放模块内，大模块拆 `tests.rs`/`mod_tests.rs`；跨模块契约测试放 `tests/` 按主题命名；复用夹具统一进 `tests/fixtures` 与 `tests/support`，禁止跨文件拷贝同一套构造代码。
- 时间相关测试使用固定时间或可注入的 `now`；随机数使用固定 seed。
- 优先断言结构化字段（错误码、状态、机器可读输出），少断言整段自然语言文案。
- 真实环境测试（真实网络、真实设备、真实外部服务）单独分层放 e2e，不与单元/集成测试混跑；失败需明确归属层级。
- 构造性验收脚本与常规测试分层执行，不混跑。

## change 任务颗粒度（唯一真源）

足够细致的颗粒度才能保证一个 change 的开发足够成功。四条硬标准：

- **原子性**：每个任务项 = 一个动作 + 一个可独立验证的结果；一条任务里藏多个子动作视为不合格，拆开。
- **约束显式化**：design/proposal 里的边界决策（「不得做 X」「只保留 Y」）必须落为可勾任务 — 不进 tasks 的约束，实现时就是靠自觉。
- **测试清单化**：测试任务独立成项，并写明覆盖清单（测哪几种情况）；「补个单测」这类笼统表述不合格。
- **复核前置**：每个 change 首块固定为复核块：与蓝图一致性、已归档 change 的复用面、现有源码回归范围、validate 基线。
- 落地体量：单 change 任务项 30-60 项为常态；块数按工作流阶段划分，不为凑块数硬合（颗粒度变细导致的块数增加不受此限）。
